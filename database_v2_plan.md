# ComNet v2 — план переходу на нове ядро обліку

**Статус:** чернетка для звірки. Код НЕ починаємо, доки не узгодили.
**Дата:** 2026-07-22
**Джерело:** `database_improvements.md` (ТЗ v1) + рішення в обговоренні.

---

## 0. Мета

Прибрати корінь майже всіх недавніх багів: **дві копії правди «хто тримає майно»**
(`items.issued_to_recipient_id` + `item_splits`). v2 розділяє облік на два чисті шари:

- **Custody** (`movements` між `warehouses`) — хто *відповідає* (склад).
- **Assignment** (`assignments` на особу) — хто *тримає на руках*. **Не рухає баланс.**

Плюс дає те, що ти просив: **багато служб** (двохосьовий доступ) і **чітке
розрізнення серійного/несерійного** (окремі `instances`).

---

## 1. Припущення (узгоджено)

1. **Чистий старт.** v2 = нова схема + wipe + новий імпорт. Поточні дані НЕ
   мігруємо — ти заливаєш заново в новому форматі.
2. **Один склад на службу і на підрозділ**, назавжди. Авто-створення: кожна
   `service` → рівно один `warehouse(type=service)`; кожен `unit` → один `warehouse(type=unit)`.
3. **Документи і вартість лишаються** (ТЗ v1 про них мовчить — ми не викидаємо).
4. **Повна заміна, без сумісності.** Старі inventory-таблиці видаляються; жодних
   дуальних кодопутей чи адаптерів до v1.

## Процес побудови

- Інтеграційна гілка **`v2`**; кожна фаза — під-бранч у неї (`feat/v2-<phase>`).
- `main` лишається на поточній робочій версії до готовності v2 end-to-end.
- Cutover наприкінці: `v2 → main` (merge --no-ff), wipe, re-import.

## Frontend — повна заміна (рішення 2026-07-24)

Проєкт ще не в роботі → UI роблять як **повну заміну**, без «v2»-суфіксів і без
паралельних екранів. v1-сторінки видаляються в міру появи заміни (разом з їхніми
роутами й UI-тестами). Кінцеве меню — суто v2.

**Цільове меню:**
| Пункт | Зміст | Замінює v1 |
|---|---|---|
| Залишки | баланси складу (custody), серійне | residues + items |
| Рухи | custody: receipt/transfer/writeoff | movements |
| Видача | assignments (видати/повернути, групи) | (нове) |
| Документи | накладні (Ф5) | documents |
| Довідники | служби/підрозділи/номенклатура/склади/МВО/групи/особи | settings (частина) |
| Налаштування | організація, типи операцій, користувачі, імпорт | settings (решта) |

## 2. Цільова схема (таблиця за таблицею)

### Довідники

**`services`** — служби (РАО, речова, зв'язку…)
`id` · `name` · `code?`

**`units`** — підрозділи (плоско, без ієрархії)
`id` · `name` · `code?`

**`groups`** — групи всередині підрозділу
`id` · `name` · `unit` FK · `commander` FK→persons (nullable)

**`persons`** — увесь особовий склад (МВО, командири, бійці, колишні позивні)
`id` · `full_name` · `callsign?` · `unit` FK · `rank?` · `group_id?` FK→groups
- Позивні (`recipients`) вливаються сюди: `callsign` = старий позивний, `unit` обов'язковий.
- «Командир групи» = person, у якого `groups.commander = він`.

**`warehouses`** — облікові точки (ядро)
`id` · `name` · `type`(service|unit) · `service?` FK · `unit?` FK
- Інваріант: `type=service` → заповнено `service`, порожньо `unit` (і навпаки).
- **Стабільний**: прив'язаний до служби/підрозділу, НЕ до особи. Ротація МВО не
  створює новий склад.

**`mvo`** — журнал призначень МВО (історичний)
`id` · `warehouse` FK(type=unit) · `person` FK · `from_date` · `to_date?`
- Діючий = `to_date IS NULL`. Максимум один діючий на склад.

### Майно

**`items`** — **номенклатура** (тип майна, не картка)
`id` · `name` · `service` FK · `is_serialized` · `unit_of_measure` · `code?` · `price?`
- `price` лишаємо (вартісний облік).
- `is_serialized` не пов'язаний з од. виміру (серійним може бути і `шт`, і `компл`).

**`instances`** — екземпляри серійного майна (1 запис = 1 предмет)
`id` · `item` FK(is_serialized=true) · `serial_no` · `current_warehouse` (денорм.) · `is_official?`
- `current_warehouse` = `to_warehouse` останнього руху; денормалізуємо (читається в ACL).
- `serial_no` унікальний глобально.

### Рух і видача

**`movements`** — рухи custody
`id` · `date` · `type`(receipt|transfer|writeoff) · `from_warehouse?` · `to_warehouse?`
· `item` FK (**завжди**, фізична колонка) · `instance?` FK · `quantity` · `is_official`
· `document_id?` FK · `signed_by?` FK→persons (снапшот МВО на момент)
- `is_official` — державне/волонтерське; для несерійного визначає лінію балансу.
- Серійне: `instance` заповнено, `quantity=1`. Несерійне: `instance` порожньо, `quantity>0`.
- `item` зберігається фізично навіть для серійного (для ACL при створенні).

**`assignments`** — видача особовому складу
`id` · `warehouse` FK(type=unit) · `person` FK · `item` FK · `instance?` FK
· `quantity` · `issued_date` · `returned_date?`
- Активна = `returned_date IS NULL`. Серійне: один активний assignment на instance.
- Інваріант: `person.unit = warehouse.unit`.

**`balances`** — залишки несерійного (VIEW, не таблиця)
`(warehouse, item, is_official) → qty` = `SUM(to) − SUM(from)` по несерійних рухах.
`is_official` — вимір балансу: державне і волонтерське одної номенклатури рахуються
окремими лініями (це «2 картки одного майна» у старій ментальній моделі).
Серійний залишок = фільтр `instances.current_warehouse`.

### Доступ

**`access_users`** — користувачі + зона
`id` · `username` · `password_hash` · `role`(admin|service|mvo)
· `service?` FK (якщо service) · `unit?` FK + `warehouse?` FK (якщо mvo) · `person?` FK
- JWT + bcrypt лишаються.

### Що зберігаємо як є (для документів)

- **`unit_settings`** — шапка організації для накладних.
- **`op_types` / `op_type_details`** — нумерація документів (`number_prefix`) + типізація
  накладної. Це шар документів, не рухів.
- **`documents` / `document_items`** — заголовок накладної + snapshot (`extra_data`).
  Ретаргетимо: документ підписується → створює `movements` між **warehouses**
  (а не free-text units); XLSX-експорт читає snapshot як зараз.
- **`asset_documents` / `item_documents`** — сканкопії (коли візьмемось).

## 3. Що ВИДАЛЯЄМО (cleanup-виграш)

- `items.issued_to_recipient_id` — дубль правди
- orphan-return синтетичний movement (hook `maybe_place_orphan_return`)
- колонка «На кому» через union двох джерел
- `POST /api/admin/backfill-splits`
- `recipients` (влиті в `persons`)
- `item_splits` (замінені на `assignments`)
- free-text `movements.from_unit` / `to_unit` / `mvo_from_id` / `mvo_to_id`

Усе це існувало, щоб латати змішування custody+assignment. v2 прибирає причину.

## 4. Модель доступу (двохосьова)

- **`service`** — бачить майно **своєї служби** в усіх підрозділах (вертикаль).
- **`mvo`** — бачить майно **свого складу** всіх служб (горизонталь).
- **`admin`** — усе.

Осі перетинаються: майно служби Б на складі 1-ї роти видиме обом.

| Таблиця | service | mvo | admin |
|---|---|---|---|
| довідники (services/units/persons/warehouses/groups) | R | R | RW |
| `mvo` | R | R | RW |
| `items` | R усі; CUD своєї служби | R | RW |
| `instances` | R+CUD своєї служби | R свого складу | RW |
| `movements` | R+C своєї служби | R свого складу; C зі свого складу | RW |
| `assignments` | R своєї служби | RW свого складу | RW |
| `balances` | R своєї служби | R свого складу | RW |

Реалізація: scoping на рівні query у FastAPI-залежностях (не тільки на UI).
Рівень застосування: спершу **м'який** (підсвітка помилок), **жорсткий**
(заборона збереження) — після стабілізації схеми.

## 5. Групи (видача «на всю групу»)

- Боєць має `group_id?`. Командир = той, кого вказано в `groups.commander`.
- У формі особи одне поле «Командує групою: [назва]» → лінкує його як commander.
- **Admin-вигляд**: клік на командира → холдинги **всієї групи** =
  `SUM(assignments) WHERE person.group_id = X AND returned_date IS NULL`.
- Членство обов'язкове для агрегації: кожен боєць групи має `group_id`, не лише командир.

---

## 6. Документи + вартість (graft поверх ядра)

- Документи = **тільки накладні** (custody склад→склад). **Видача особі —
  БЕЗ документа** (варіант A, рішення 2026-07-22); роздавальна відомість —
  можливо в майбутньому, не в цьому обсязі.
- Накладна `transfer` при підписі → `custody_movement(from_warehouse=склад-відправник,
  to_warehouse=склад-отримувач)`. Накладна `receipt` → рух у склад служби.
- Вибір складів у формі документа замість free-text підрозділів.
- Snapshot (`extra_data`) морозить поля відображення як зараз; XLSX без змін логіки.
- `price` на `nomenclature` → суми, пропис (`uk_num2words`) лишаються.

## 7. Новий формат імпорту

Оскільки `items` тепер номенклатура, а видача — `assignments`, імпорт розбивається:

**Один файл Items** (як зараз), розкладається на кілька сутностей при парсингу:
- рядок = номенклатура (+ `instance`, якщо серійне);
- колонка **«Де»** = `<підрозділ> [<людина>]`:
  - підрозділ визначає **склад-локацію** → синтезуємо рух у склад цього підрозділу;
  - людина (якщо є) → `assignment` на неї (її `unit` = той самий підрозділ);
  - без людини → лежить на складі підрозділу, нікому не видано.

**Парсинг «Де»:** матч **найдовшої відомої назви `units`** на початку клітинки,
залишок = ПІБ/позивний. Тому `units` мають бути заведені (фаза 1) ДО імпорту (фаза 6),
названі так само, як у файлі. Колонка «Де» — джерело і підрозділу, і тримача
(замінює стару окрему логіку «Видано»).

один раз. Життєвий цикл: draft → signed (snap заморожено, номер зафіксовано,

фічею «рух без накладної → документ потім»).

в STATE.md):
- `is_official` (облік/ндм) — властивість **картки** (nomenclature), не вимір
  балансу (рухи/екземпляри успадковують).
- Імпорт: Items = **каталог** (без розміщення); розміщення — окремим файлом
  **Переміщень** (щоб не подвоювати). Матч серійного по **картці** (№ ↔ «Поле 12»).
- Видача особі — **без документа** (рішення); batch-«Видати в підрозділ» = накладна переміщення.
